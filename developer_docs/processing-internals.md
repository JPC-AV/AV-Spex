# AV Spex — Processing Internals

Deep reference for the analysis subsystems. CLAUDE.md carries a one-paragraph summary of each; the full detail lives here. Read this when working **inside** frame analysis, qct-parse, or CLAMS detection.

---

## Frame Analysis (`checks/frame_analysis.py`)

Unified module controlled by `FrameAnalysisConfig`. Three optional sub-steps, each independently togglable:

- **Border detection**: Detects active video area and head-switching artifacts. Modes: `simple` (fixed pixel crop, default 25px) or `sophisticated` (edge detection). Supports auto-retry with refinement iterations.
- **BRNG analysis**: Detects out-of-range luma/chroma values using multi-method voting; generates diagnostic thumbnails and an HTML report with magenta highlights.
- **Signalstats**: FFmpeg `signalstats` filter analysis over selected time periods (default: 3 periods of 60s each).

Signalstats and BRNG analysis sample **analysis periods** rather than the whole file. How those periods are chosen — the QCTools violation histogram, the black-segment/bars avoidance and repair passes, and the post-signalstats refinement — is documented separately in **`developer_docs/analysis-period-selection.md`**.

Color bars end time (from qct-parse) is passed to frame analysis so non-program content is skipped. Results feed into the HTML report.

Frame analysis image/JSON outputs (`_enhanced_frame_analysis.json`, `_border_detection.jpg`, `brng_thumbnails/`) are written to **`{video_id}_qc_metadata/`**, not `report_csvs/` — `analyze_frame_quality(output_dir=destination_directory)` and `destination_directory` is the qc_metadata dir (see `dir_setup.py`). Some frame-analysis CSV sidecars and HTML fragments do go to `report_csvs/`.

## qct-parse Subsystem (`checks/qct_parse.py`)

`qct_parse.py` is the largest single module in the codebase (~3000 lines). It is **not** just a "tool check" — it is its own subsystem that walks the QCTools sidecar (`.qctools.xml.gz` / `.qctools.mkv`) once and runs several optional analyses against it. All sub-features are controlled by flags on `QCTParseToolConfig`. Entry point: `run_qctparse(video_path, qctools_output_path, report_directory, …)`. The module derives from the open-source [qct-parse](https://github.com/FutureDays/qct-parse) project; substantial pieces have been rewritten or added on top.

Sub-features (each independently togglable):

- **Color bars detection** (`barsDetection`): `detectBars()` walks the report looking for SMPTE color bars at the head, writes start/end timestamps to `qct-parse_colorbars_durations.csv`. The end time is downstream-consumed by frame analysis and access-file generation so bars are skipped.
- **Color bars evaluation** (`evaluateBars`): `evalBars()` walks the detected bars region and, for eight level keys (`YMAX/YMIN/UMIN/UMAX/VMIN/VMAX/SATMIN/SATMAX`) plus `BRNG`, computes the **median** value across all measured frames — returned as `maxBarsDict`. The level medians are written alongside the reference SMPTE values to `qct-parse_colorbars_values.csv` (via `print_color_bar_values`); the whole dict, `BRNG` included, is handed to `analyzeIt()` as the thresholds content frames are graded against (the bars regions themselves are excluded via `skip_regions`). See the median-threshold and BRNG gotchas below.
- **Threshold-based tag checks** (`analyzeIt()`): for each profile tag in `SpexConfig.qct_parse_values`, count frames where the value exceeds/under-runs the threshold. Mismatches are summarized in `qct-parse_failures.csv` and `qct-parse_summary.csv`.
- **Thumbnail export** (`thumbExport`): `printThumb()` writes a JPEG snapshot when a threshold is crossed (rate-limited via `thumbDelay`/`thumbExportDelay`). Saved under `ThumbExports/` in the report directory; `find_qct_thumbs()` in the report generator surfaces them.
- **Audio analysis** (`audio_analysis`): `analyzeAudio()` runs five independent detectors over a single pass of the QCTools tags. For **multi-stream inputs** (e.g. broadcast MXF, where each channel is a discrete mono stream) the QCTools report's audio frames only describe a qcli downmix, so `run_qctparse()` instead generates (or reuses, if present) a per-stream stats sidecar `{video_id}.audio_stats.xml.gz` in `_qc_metadata/` via `checks/audio_stream_stats.py` and runs `analyzeAudio()` on that file — see the gotcha below. Each detector writes its own CSV/summary and HTML report subsection:
    - **Clipping** — flags frames where `Peak_level ≥ AUDIO_CLIPPING_THRESHOLD_DB` (default −0.5 dBFS).
    - **Channel imbalance** — compares per-channel `RMS_level` and flags sustained level differences across channels.
    - **Audible timecode (LTC)** — detects LTC bleed-through. Uses **two layers**: R128 mix-loudness gates (`r128.M`, `r128.M_mean`, `r128.M_stdev`, `r128.LRA`) for "stable mix at TC level", plus per-channel `astats` gates (`Crest_factor`, `Zero_crossings_rate`, `RMS_level`, `Entropy`) for the per-channel split. Thresholds are calibrated against three known-TC samples and two non-TC negatives; constants live at the top of the audio section in `qct_parse.py:1057–1119`. The `astats` layer runs in two stages: a coarse 30s rolling-window pass (`_detect_astats_channel_tc`) finds TC *territory* but its stdev stability gate is poisoned by brief dropouts (a ~3s real gap reads as a ~100s hole), so `_tc_refine_astats_gaps()` then re-scans each region per frame — a frame is TC only if all four metrics sit in their bands (`_tc_frame_in_band`), and a region is split only on a *sustained* non-TC run (`_TC_GAP_MIN_SEC`, default 2s, after merging runs separated by a sub-second TC flicker). This reclaims TC the window dropped around a brief interruption and pins gap boundaries to the frame. The two layers fire redundantly over the same TC, so their overlapping detections are collapsed into **consensus regions** by `_tc_build_consensus()` — conceptually the qct-parse/CLAMS color-bars consensus, but **astats is privileged for segmentation**: the per-channel astats boundaries are authoritative (astats resolves true breaks where the carrier stutters or one channel drops out, which the mix-based R128 meter smooths over), and R128 is demoted to corroboration — it only adds the `R128` method label where it overlaps an astats region. A standalone R128 span (no astats overlap) is kept **only when the report has no per-channel astats data** (older QCTools reports); when astats data is present, an uncorroborated R128 detection is discarded as a false positive — the R128 loudness gates alone can't tell LTC from other steady-loudness audio (heavily compressed music passes criterion A; quiet speech over a near-silent channel passes criterion C — both confirmed false-positive regimes, in sample files JPC_AV_03796/03801 and LC 21459403/21462335 respectively), and "Audible Timecode Detected" follows the consensus regions, not the raw per-method list. `qct-parse_audible_timecode.csv` leads with the consensus table (last column *Detection Methods*) and keeps the raw per-method detections in a trailing *Per-Method Detections* section; the HTML report shows only the consensus regions. Region **Start/End are written as the file's own timecode** — NDF `HH:MM:SS:FF` or DF `HH:MM:SS;FF` (`_tc_format_timecode`) — so positions match an NLE; the *Duration* column stays elapsed `M:SS.s`. Frame rate comes from `_get_video_frame_rate` (default NTSC 29.97); the **start-timecode offset and drop-frame flag are read from the stream's TIMECODE tag** via `_get_video_start_timecode` + `_tc_parse_start_timecode` (`;` before frames ⇒ drop-frame), threaded `run_qctparse → analyzeAudio → _detect_and_write_timecode_results`. QCTools timestamps are real wall-clock seconds, which read ~0.1% (~3.6s/hour) *ahead* of the NDF timecode an NLE shows — converting to a frame index, adding the start-TC offset, and re-labelling in the file's convention removes that apparent drift. DF math (`_tc_df_to_frames`/`_tc_frames_to_df`) drops 2 frame-numbers/minute except every 10th (4 at 60 fps).
    - **Identical channels (dual mono)** — flags two channels carrying the same audio. **Two stages.** The *screen* rides the same parse: on every frame with audio, each channel pair is compared on its `astats` `RMS_level` (match within `IDENTICAL_RMS_TOLERANCE_DB`, default 0.1 dB) and, for stereo only, `lavfi.aphasemeter.phase` (|phase| ≥ `IDENTICAL_PHASE_THRESHOLD`, default 0.999 — near +1 is a duplicate, near −1 a polarity-inverted one). Frames where every channel is at or below `IDENTICAL_SILENCE_FLOOR_DB` are excluded (silence matches silence trivially) but do *not* break a matching run, so a silent gap inside a duplicated passage stays one region. A pair matching ≥ `IDENTICAL_FULL_MATCH_FRACTION` (99%) of active frames screens as a whole-file candidate; ≥ `IDENTICAL_PARTIAL_MATCH_FRACTION` (10%) with a run of at least `IDENTICAL_MIN_SPAN_SEC` screens as partial. The *confirmation* stage then decodes the two channels through one ffmpeg pipe (`_measure_channel_difference` — `pan=stereo` off the single stream, or `amerge` of all streams in sidecar order then `pan`, so channel N is stream N as elsewhere; **no resampling**, the comparison has to see the original samples) over the whole file (full candidates) or the longest matching span (partial ones), measuring the peak/RMS of both **A−B and A+B**. A residual at/below `IDENTICAL_BIT_IDENTICAL_PEAK_DB` is *Bit-identical*; at/below program peak − `IDENTICAL_EFFECTIVE_MARGIN_DB` (30 dB) is *Effectively identical*; anything louder means the screen was wrong and the pair is reported *Distinct channels* — **the sample comparison is authoritative over the screen**. Which residual cancels tells a straight duplicate (A−B) from a polarity-inverted one (A+B); astats alone cannot separate those. Without a decodable `video_path` the verdict is still reported but labelled *(unconfirmed)*. At most `IDENTICAL_MAX_CONFIRM_PAIRS` pairs are confirmed so a many-channel file can't spawn a pile of decodes. Sidecar: `qct-parse_identical_channels.csv` (summary block + per-pair table + matching regions, whose Start/End are the file's own timecode). No separate config flag or CLI toggle — it runs with `audio_analysis`.
    - **Audio dropout** — flags sudden RMS drops indicative of tape dropout. Uses a **rolling median baseline** of RMS / max-RMS-diff / zero-crossings-rate, then flags single-frame deviations against thresholds (`DROPOUT_RMS_DROP_THRESHOLD_DB`, `DROPOUT_DIFF_DROP_FACTOR`, `DROPOUT_ZCR_SPIKE_FACTOR`). Candidates are merged into events.
- **Clamped-levels detection** (`detect_clamped_levels`): finds runs of frames whose luma is clamped to broadcast range (16–235 in 8-bit / 64–940 in 10-bit). Outputs a graph and summary if hits are found.
- **Chroma phase error detection** (`detect_chroma_phase_errors`): `analyzeChromaPhaseErrors()` detects sudden cyan/magenta colour shifts typical of helical-scan tracking failures on tape sources. Two-rule detector per frame:
    1. **Envelope-wide (primary):** within a single frame, both U and V span nearly the full chroma range (`UMIN < CHROMA_ENVELOPE_LOW` AND `UMAX > CHROMA_ENVELOPE_HIGH` AND same for V).
    2. **SATMAX high (secondary):** catches partial-frame events where only part of the frame is in error.
  Thresholds are defined for 10-bit (0–1023) and scaled /4 for 8-bit. Consecutive flagged frames within `CHROMA_EVENT_GAP_FRAMES` are merged into a single event; events shorter than `CHROMA_MIN_EVENT_FRAMES` are suppressed as false-positive transients. Up to `CHROMA_MAX_THUMBS` event thumbnails are written to `ChromaPhaseThumbs/` (kept separate from `ThumbExports/` so the generic thumb finder doesn't pick them up). Sidecar CSVs: `qct-parse_chroma_phase_summary.csv`, `qct-parse_chroma_phase_events.csv`. GUI checkbox lives on the Complex tab; CLI flag is `--enable-chroma-phase-detection`.

### qct-parse gotchas

- **`detectBars()` threshold rationale**: `YMAX_thresh` / `YMIN_thresh` / `YDIF_thresh` detect luma characteristics of SMPTE bars. `SATMAX_thresh` is the key discriminator — it distinguishes real color bars (high saturation) from static or near-black frames that happen to meet the luma criteria. `bars_confirmation_threshold` (30 frames ≈ 1s at 30fps) prevents false starts from analog artifacts. The `relaxed=True` flag halves confirmation, lowers SATMAX by 60%, and doubles YDIF tolerance — use it for CLAMS-guided retries where bars existence is already probable. **Don't chase the strict YDIF threshold (8.0)**: real JPC head bars measure YDIF ≈ 8.3–11 and routinely fail the strict pass — that's expected, the CLAMS-guided relaxed retry handles them — while saturated slates sit right at 8.0, so no YDIF value separates bars from slate (JPC_AV_01056: bars 8.27 vs slate 8.01). SSIM separates them cleanly; let the consensus own the boundary. **Short-candidate abandonment**: once a start is confirmed, ending a region needs `failure_tolerance` consecutive misses *and* >2s duration — a candidate that accumulates the misses while still under 2s is abandoned and the search resumes. (Before this fix, the region could never terminate, and one stray passing frame minutes later dragged `durationEnd` across arbitrary content — the source of JPC_AV_01056's phantom 52.8–75s head bars.)
- **`make_color_bars_graphs()` implicit contract**: depends on three inputs that must describe the same bars region: the duration CSV (for the timestamp annotation), the values CSV (for the bar chart data), and the thumbnails dict (for the first-frame image). Passing mismatched inputs (e.g., head-bars duration CSV with a windowed-bars values CSV) silently produces wrong output. Use `duration_override`, `bars_label`, and `thumb_profile_filter` parameters to control which data each graph shows.
- **`print_color_bar_values()` CSV column naming**: the detected-bars column header is `{video_id} Colorbars` (hardcoded in `qct_parse.py`). Code that reads this CSV (e.g., `make_color_bars_graphs`) must use this exact pattern to look up the column.
- **Color-bars evaluation thresholds are the median of the detected bars, not the peak** (`evalBars()`): each of the eight keys is the **median across every measured frame** in the detected bars region (`statistics.median`, rounded to int). This replaced the original per-key peak (max for `*MAX`, min for `*MIN`), where a single extreme frame defined the threshold. The median (over the mean) was chosen for robustness against transient outliers — chiefly the frames where the bars "crash" in/out; the `buffSize` frame-buffer gate additionally drops the leading crash-in frames before the median is taken. **Consequence:** median thresholds sit in the *middle* of the bars rather than at their extreme, so they are **tighter** than the old peak — content merely hotter/more-saturated than typical bars now trips the evaluation, and per-file failure rates run correspondingly higher than under peak logic. This tightening is inherent to any central-tendency threshold and is near-identical whether mean or median is used (on the JPC sample set — 01056/01772/01823/02212/03796 — mean and median agree to within 3 units on the 0–1023 10-bit scale, because those bars are stable and the buffer already removes crash-in). Keys with no measured frames fall back to a permissive extreme (`0` for `*MAX`, `1023` for `*MIN`) so the threshold never rejects everything.
- **Where the `smpte_color_bars` config values come from**: they are **measured from an ffmpeg-generated 10-bit SMPTE bars reference**, not taken from a standards document. `sample_files/color_bars/ffmpeg_generated/color_bars_v210.mov` reproduces the shipped config exactly on all eight level keys (YMAX 940, YMIN 28, UMIN 148, UMAX 876, VMIN 124, VMAX 876, SATMIN 0, SATMAX 405 — every frame identical, min == median == max). (`VMAX` shipped as `867` from the config's introduction in 2024 until July 2026, when measuring the reference showed it to be a digit transposition of `876`; corrected then.) The other two files in that directory are *not* usable as references: the ffv1 8-bit encode carries a differently-saturated pattern (UMIN ×4 = 176 vs 148) and the MPEG-2 encode adds compression noise (values vary frame to frame). Add a new key by measuring the v210 file, not by reasoning from the spec.
- **BRNG in the color-bars evaluation is handled unlike the level keys** (`evalBars()` + `print_color_bar_values()`): `BRNG` is the *share of out-of-range pixels* (0–1), not a level on the 0–1023 scale, so (a) its median keeps float precision (rounding to int would zero it), (b) it is **floored at `SpexConfig.qct_parse_values.smpte_color_bars.BRNG`**, and (c) it is **excluded from `qct-parse_colorbars_values.csv`** (`BARS_NON_LEVEL_KEYS`) so it doesn't plot as an invisible bar next to YMAX/SATMAX in the detected-vs-SMPTE graph. **A correct SMPTE bars signal is not free of out-of-range pixels**: the v210 reference measures BRNG `0.011806` on every frame (identically in the ffv1 encode) — the PLUGE and the 100% saturated patches sit outside broadcast range by design. That measured value (rounded to `0.0118`) is the config default and the floor; note it is *above* the `> 0.01` threshold `frame_analysis.py` uses to count a BRNG violation, i.e. reference bars would themselves register as violating frames — one more reason bars regions are excluded from BRNG analysis. The floor keeps a bars region measuring below the reference from driving the threshold toward zero, where every content frame would fail. `qct_parse.SMPTE_BRNG_DEFAULT` is a backstop for a missing/malformed config value and is pinned to the shipped config by a test. Effect on the report: the eval-bars **failure timeline** gains a dashed teal `BRNG` trace, which is the *same* measure that drives frame analysis's analysis-period placement, so the trace and the shaded period bands should visibly coincide — that alignment is the point of including it. Sample failure rates: JPC_AV_01581 (bars median 0.0306, above the floor → used as-is) 1.2% of content frames; JPC_AV_01056 (bars median 0.0076 → floored to 0.0118) 35%.
- **Multi-stream audio fallback (`checks/audio_stream_stats.py`)**: when `_get_audio_stream_count()` reports >1 audio stream, audio analysis reads a generated sidecar instead of the QCTools report. `generate_audio_stats_sidecar()` decodes every audio stream in one `ffprobe -f lavfi` pass — a single `amovie` source selecting all streams (`s=1+2+…`, **bare absolute stream indexes**: `a:N`-style specifiers fail amovie's option parsing even escaped/quoted) fed through `amerge` so astats channel N = audio stream N, the same 1-based channel↔stream mapping `make_access.py`'s multi-mono handling assumes. Filter-chain constraints (inherited from `developer_docs/make_signalstats_xml.py`, this module's one-off ancestor): **astats must come first** (aphasemeter/ebur128 collapse the signal to a stereo downmix; astats metadata attached earlier survives), **no `asetnsamples`** (reframes the stream and drops per-channel astats metadata); ebur128's 100ms cadence drives ~10 fps audio frames, matching qcli's cadence — verified on JPC_AV_01772 (stereo split into 2 mono streams): dropout/imbalance results are identical to the qcli-report path. Per-frame astats reports `-inf` for digitally silent frames, which would poison a channel's arithmetic RMS mean, so values are floored to `SILENCE_FLOOR_DB` (−120 dBFS — below every silence/dropout/LTC threshold). The write goes to a `.part` temp name and is renamed only on success, so the reuse-if-present check never picks up a truncated file; delete the sidecar to force regeneration. The generated file's timestamp attribute is detected by `_detect_audio_pkt()` (audio-frame analogue of run_qctparse's video-frame `pkt_.ts_time` sniff). Generation failure falls back to the old behavior: audio analysis is skipped with a warning (never silently analyzed from the downmix).
- **Reporting a media time *position* to the user — use the file's timecode, not wall-clock seconds.** QCTools `pkt_pts/pkt_dts` values are real elapsed seconds. An NLE (DaVinci Resolve, etc.) shows the file's embedded timecode, which for NTSC NDF runs ~0.1% (~3.6 s/hour, ~2 s at 36 min) *behind* wall time, plus any start-TC offset. Printing raw seconds therefore looks "ahead of the NLE, growing with runtime" — this is *not* a bug, it's the format mismatch. The audible-timecode path does it correctly: `_tc_format_timecode(seconds, fps, start_frames, drop_frame)` converts to a frame index, applies the start-TC offset, and re-labels NDF (`HH:MM:SS:FF`) or DF (`HH:MM:SS;FF`); inputs come from `_get_video_frame_rate` + `_get_video_start_timecode` + `_tc_parse_start_timecode`. **`dts2ts()` (used by color bars, audio dropout, chroma-phase events, thumbnails) still emits raw `HH:MM:SS.ssss` wall-clock seconds and has this drift** — anything new that surfaces a position to the user should prefer the `_tc_format_timecode` path. Durations/intervals can stay elapsed seconds (the drift on a short span is negligible and a duration isn't a timecode position).

## CLAMS Detection (`checks/bars_detection_clams.py`, `checks/tone_detection_clams.py`)

Sits parallel to the qct-parse color-bars/tone analysis but is independent (separate `clams_detection: ClamsDetectionConfig` field; toggled via `--enable-clams-detection`). Two scripts:

- **`bars_detection_clams.py`**: SSIM-based color bars detection against a bundled reference fingerprint. Tunables in `ClamsBarsParams`: `threshold` (SSIM), `sample_ratio`, `stop_at_frame`, `min_frame_count`, `stop_after_one`, `merge_gap_seconds`. Outputs: `clams_bars_colorbars_durations.csv` (thresholded runs, one row per pass — labels `primary`, `head-second-pass`, `second-pass`) and `{video_id}_clams_bars_ssim_scores.csv` — one row per sampled frame (`pass,frame,timestamp,ssim_score,exceeds_threshold`), appended across passes (`primary`, `second-pass`, `verify`). **The scores CSV is load-bearing, not just diagnostic**: `runs_from_recorded_scores()` replays it at a lower threshold for the relaxed head re-check (no video decoding), and the merge's `_clams_max_ssim_in_span()` reads it to arbitrate detector disagreements. **SSIM is computed by a local `structural_similarity()` (scipy.ndimage-based) at the top of this module — NOT scikit-image. It is a verified bit-identical reimplementation of skimage's default 2D path; do not re-add the `scikit-image` dependency.**
- **`tone_detection_clams.py`**: cross-correlation tone detection over the audio waveform (loaded mono @ 16 kHz). Tunables in `ClamsToneParams`: `tolerance`, `min_tone_duration_ms`, `stop_at_seconds`, `merge_gap_seconds`. Output: `clams_tone_detection_durations.csv`.

The numeric tuning fields above are **CLI-unsettable** — `update_tool_setting()` only accepts `clams_detection.run_tool`. Tune them in the JSON config or via the GUI.

### Combined bars/tone detection pipeline ordering & head-bars consensus

CLAMS detection runs before qct-parse in `process_qctools_output()`. Consensus tuning constants live at the top of `processing_mgmt.py`: `HEAD_BARS_START_THRESHOLD` (30.0s — bars starting later aren't "head" bars), `HEAD_END_AGREEMENT_SLACK` (3.0s), `CLAMS_SSIM_CORROBORATION_MIN` (0.55), `CLAMS_HEAD_RESCAN_SECONDS` (120.0), `SECONDARY_BARS_THRESHOLD` (0.6), `SECONDARY_BARS_SAMPLE_RATIO` (5). Phases:

1. **CLAMS tone** — whole file, fast.
2. **CLAMS bars primary** — from frame 0, `stop_after_one`; its first hit is *not necessarily at the head* (it can be mid-file bars).
3. **CLAMS relaxed head re-check (phase 2b)** — if no primary run starts within `HEAD_BARS_START_THRESHOLD`, `runs_from_recorded_scores()` replays the already-recorded SSIM samples over the first `CLAMS_HEAD_RESCAN_SECONDS` at the relaxed 0.6 threshold (zero decoding; raw scores are threshold-independent). Hits are written as `head-second-pass` rows and become the CLAMS head candidate. Exists because real degraded head bars can score a hair under the 0.7 primary threshold (JPC_AV_01056: 0.696–0.699).
4. **Cross-validation second passes** — relaxed bars scans over tone regions not covered by known bars; relaxed tone scans over bars regions not covered by tones (±5s slack).
5. **qct-parse bars detection** — receives all CLAMS regions via `clams_regions`. Strict head pass first; if it misses but CLAMS has head-window bars, a `relaxed=True` retry runs over the CLAMS head *cluster* (runs chained within 30s of each other, so tail bars don't stretch the window). The retry is a **confirmation pass, not discovery**: start/end are clamped to the CLAMS boundaries ±1s, because relaxed luma thresholds can't tell bars from a saturated slate and otherwise ride out to the search-window edge. Windowed "additional" scans then run only on CLAMS regions that don't *overlap* the detected head bars (an overlapping region is the head sequence itself — tone routinely outlasts head bars; a remainder is scanned only if it extends ≥30s past the head). Failed windows retry relaxed.
6. **Merge — SSIM-arbitrated consensus, not `max()`**: the CLAMS head candidate is classified by time (earliest run starting `< HEAD_BARS_START_THRESHOLD`, whatever its pass label). Ends within `HEAD_END_AGREEMENT_SLACK` agree (later wins). A larger disagreement is arbitrated by `_clams_region_is_bars()` over the disputed span: max recorded SSIM `< CLAMS_SSIM_CORROBORATION_MIN` means the extension isn't bars → the earlier end wins. A **qct-parse-only head claim that CLAMS decisively contradicts is demoted**: logged as unconfirmed, kept in the durations CSV, but `color_bars_end_time` stays `None` so it never drives access-file trim or BRNG-skip. When the recorded scores don't cover the claimed span, a targeted `verify` scan (0.6 threshold) runs and appends to the scores CSV. Mid-file bars never drive `color_bars_end_time` (no access-file trim from them).

**Downstream exclusion of bars regions**: `process_qctools_output()` exports the merged bars spans from both detectors (a demoted head claim is dropped) as `results['all_bars_regions']`. These flow through `process_video_outputs()` → `process_frame_analysis()` → `analyze_frame_quality(bars_regions=…)`, where they join the black-segment avoid-list: analysis periods are placed/shifted away from them (the shared shift policy tolerates <10% residual overlap per period), BRNG violation parsing skips frames inside them (`parse_for_violations_streaming(exclude_regions=…)`), and duplicate-frame candidates inside them are dropped (`find_duplicate_frame_candidates` exclusion list). Inside qct-parse, the color-bars evaluation passes `skip_regions=all_bars_regions` to `analyzeIt()` so only content frames are scored against the bars-derived thresholds — scoring bars against bars is self-referential (on JPC_AV_01823 this removed ~580 YMAX "failures" that were just the tail bars flagging against the head-bars values). **Chroma-phase detection and access-file trimming intentionally keep using only the head end time.** Audio dropout suppression separately consumes qct-parse's own `all_bars_regions` list inside `analyzeAudio()`.

The HTML report's bars comparison table (`make_bars_detection_comparison_html`) mirrors this: rows are sorted chronologically, and head candidates are classified by the same 30s time window, not by pass label.

Calibration ground truth (see also the memory file / July 2026 work): JPC_AV_02212 (bars 0:00–0:15, SSIM 0.85) and JPC_AV_01056 (bars 0:08–0:18 at SSIM 0.696–0.699, saturated slate after, tail bars 2:37–2:39 at 0.7005).

## QCTools Report Discovery

`find_qctools_report()` in `processing_mgmt.py` searches both `{video_id}_qc_metadata/` and `{video_id}_vrecord_metadata/` before generating a new report. If an existing report is found, it is used and the run-tool step is skipped.
